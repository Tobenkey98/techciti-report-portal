# TechCiti Tutor Report Portal — API

Backend for the TechCiti tutor report portal. Node 20+, Express, TypeScript
(ES modules), Prisma and MySQL/MariaDB.

It serves **two deliberately separate surfaces** from one codebase:

| Surface | Prefix | Who calls it | How it authenticates |
| --- | --- | --- | --- |
| Admin app | `/api/admin/*` | The admin portal (`/login`, `/admin`) | JWT in an httpOnly session cookie |
| Tutor app | `/api/tutor/*` | The tutor portal (`/t/<token>`) | The tutor's private token in `X-Tutor-Token` |

The two never mix: the tutor namespace never returns an admin URL, never
exposes an admin credential, and rejects requests carrying the admin origin.
The two front ends are deployed on separate origins and are expected to stay
that way.

Terminology is fixed throughout the API and database: **course** (never
*subject*) and **level** (never *grade*).

## Quick start

```bash
cd backend
cp .env.example .env          # then edit DATABASE_URL, JWT_SECRET, the origins
npm install
npm run setup                 # prisma generate + db push + seed
npm run dev                   # http://localhost:4000
```

`npm run setup` is the three commands in a row. Run them individually if you
prefer.

Check it is alive:

```bash
curl http://localhost:4000/api/health
```

### Credentials after seeding

`npm run seed` prints the super admin email/password it created (taken from
`SUPER_ADMIN_*` in `.env`) and a ready-to-open portal link for each of the five
demo tutors. Copy them from that output — they are not stored anywhere else.

```
Super admin   admin@techciti.ng / TechCiti2026!
Tutor portal  http://localhost:3000/t/<48-hex-token>
```

### Database without the CLI

Some shared hosts only give you phpMyAdmin and no shell. `database/schema.sql`
is a plain MySQL dump of the same schema for that case:

1. Create an empty database `techciti_reports` (utf8mb4).
2. **Import → Choose File → `backend/database/schema.sql`.**
3. Run `npm run seed` afterwards to load demo data.

`database/schema.sql` is generated by `npm run db:sql`, which shells out to
`prisma migrate diff`. It is never hand-edited, so it cannot drift from
`prisma/schema.prisma`. **Re-run `npm run db:sql` after any schema change.**

### Verifying an install

With the server running:

```bash
node scripts/smoke.mjs
```

89 assertions covering auth, origin isolation, every resource, the tutor
write flow, the review workflow, documents and bulk import. It is safe to
re-run. It does write a few rows of its own (`Smoke Test…` tutors/students)
because the report-submission flow cannot be undone through the API; those are
deleted or deactivated at the end of each run. `npm run seed -- --reset`
restores a pristine database.

## Configuration

Everything is read from `.env` by `src/config/env.ts`, which validates the file
with zod at boot — a missing or malformed value stops the process with a
readable message instead of failing later at runtime. There is **no `dotenv`
dependency**: Node's built-in `process.loadEnvFile()` is used, with a small
parser fallback for older runtimes.

| Variable | Default | Notes |
| --- | --- | --- |
| `NODE_ENV` | `development` | `test` disables rate limiting |
| `PORT` | `4000` | |
| `DATABASE_URL` | `mysql://root:@localhost:3306/techciti_reports` | XAMPP default credentials |
| `JWT_SECRET` | — | **Required.** `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
| `JWT_EXPIRES_IN` | `8h` | Admin session lifetime |
| `COOKIE_NAME` | `techciti_admin_session` | |
| `COOKIE_SECURE` | `false` | Set `true` once the API is on HTTPS |
| `SUPER_ADMIN_NAME/EMAIL/PASSWORD` | — | Used only by `npm run seed` |
| `ADMIN_ORIGIN` | `http://localhost:3001` | The only origin allowed on `/api/admin/*` |
| `TUTOR_ORIGIN` | `http://localhost:3000` | The only origin allowed on `/api/tutor/*` |
| `TUTOR_PORTAL_URL` | `http://localhost:3000` | Builds `…/t/<token>` share links |
| `DEFAULT_TIMEZONE` | `Africa/Lagos` | Month boundaries and "today" |
| `MAX_MONTHS_AHEAD` | `0` | Cap on how far ahead a report may be written |

## Data model

`prisma/schema.prisma`. InnoDB, `utf8mb4`, `createdAt`/`updatedAt` everywhere.

- **admins** — `SUPER_ADMIN` | `ADMIN`, unique email, bcrypt hash, `lastLoginAt`.
- **tutors** — unique `accessToken` (48 hex chars), `tokenRevokedAt`, `isActive`.
- **students** — `ageGroup`: `KIDS` | `TEENS` | `ADULTS`; optional parent contact.
- **courses** — unique name + category, `isActive`.
- **assignments** — tutor × student × course with a `level`
  (`BEGINNER` | `INTERMEDIATE` | `ADVANCED`). Unique on all three columns, so a
  tutor cannot be assigned the same course to the same student twice.
- **reports** — one row per `(assignmentId, month)`. Month is `CHAR(7)`
  `YYYY-MM`. Carries the tutor's answers, `progressRating`, `sessionsHeld`,
  `sessionsAttended`, and a `status` of `DRAFT` → `SUBMITTED` → `REVIEWED`, or
  `NEEDS_REVISION` when an admin sends it back.
- **activity_logs** — append-only audit trail (`actorType`, `action`,
  `entityType`, `entityId`, JSON `meta`).

Reports hang off **assignments**, not directly off tutors or students. A tutor
can teach the same student different courses, and each needs its own monthly
report, so the assignment is the only correct parent.

Records that own reports are never hard-deleted — the API returns `409` and
points at deactivation, because the report history is the product.

## Authentication

### Admin — cookie session

`POST /api/admin/auth/login` sets an httpOnly, `SameSite=Strict` cookie
(`Secure` once `COOKIE_SECURE=true`) holding a JWT scoped to `aud:
techciti-admin`. Login is limited to **5 attempts per 15 minutes keyed on IP
*and* email**, so neither one noisy IP nor one targeted account can grind
through the password space. The admin is re-read from the database on every
request, so deactivating an admin or changing their password takes effect
immediately rather than at token expiry.

### Tutor — private token

A tutor's whole portal is one URL: `TUTOR_PORTAL_URL + /t/<accessToken>`. The
front end puts that token in `X-Tutor-Token` on every call. The server resolves
the tutor from the database on **every** request and rejects revoked or
inactive tokens.

Two consequences worth knowing:

- Rotating a link (`POST /api/admin/tutors/:id/regenerate-link`) instantly kills
  the old one, because lookup is an exact match on the stored token. It does
  **not** set `tokenRevokedAt` — that field describes the stored token, and the
  stored token is about to be a new, valid one. Setting it would hand the admin
  a dead link.
- Deactivating a tutor does set `tokenRevokedAt`; reactivating clears it and
  restores the same link.

Every tutor query is scoped to the resolved tutor's id. Another tutor asking
for a foreign assignment gets **404, not 403** — a 403 would confirm the id
exists.

## CORS, and why it is not the security boundary

`/api/admin/*` answers only `ADMIN_ORIGIN`; `/api/tutor/*` answers only
`TUTOR_ORIGIN`. A cross-origin call to the wrong namespace gets `403` before any
handler runs. Requests with **no** `Origin` header are allowed, so server-to-
server callers, curl and the smoke test work.

CORS is a browser feature, not access control. The real boundaries are the
session cookie (`SameSite=Strict`, and `Secure` in production) and the tutor
token. Anyone who holds a valid token can call the API from anywhere; that is
the intended design for a link a tutor pastes into WhatsApp.

## Response format

Success:

```json
{ "success": true, "data": { } }
```

Failure:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Some fields need attention.",
    "details": { "topicsCovered": "Tell us what you covered." }
  }
}
```

List endpoints return the payload under `data`:

```json
{
  "success": true,
  "data": {
    "rows": [],
    "total": 0, "page": 1, "pageSize": 20, "pageCount": 0,
    "hasNext": false, "hasPrevious": false
  }
}
```

| Code | HTTP |
| --- | --- |
| `VALIDATION_ERROR` | 422 |
| `UNAUTHORIZED` | 401 |
| `FORBIDDEN` | 403 |
| `NOT_FOUND` | 404 |
| `CONFLICT` / `DUPLICATE_REPORT` | 409 |
| `RATE_LIMITED` | 429 |
| `BAD_REQUEST` | 400 |
| `INTERNAL_ERROR` | 500 |

Timestamps are ISO 8601 in `Africa/Lagos`. Nulls are `null`, never `""`.

### Tutor — `X-Tutor-Token: <token>`

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/api/tutor/me` | The tutor behind the token |
| `GET` | `/api/tutor/assignments?month=` | Cards, per-month status, summary counts |
| `GET` | `/api/tutor/reports/:assignmentId?month=` | `data.report` is `null` if unwritten |
| `GET` | `/api/tutor/reports/:assignmentId/previous?month=` | Last month, for continuity |
| `PUT` | `/api/tutor/reports/:assignmentId` | Autosave; upserts a `DRAFT` |
| `POST` | `/api/tutor/reports/:assignmentId/submit` | Validates, then locks the month |

Editing is allowed **only** while a report is `DRAFT` or `NEEDS_REVISION`;
`SUBMITTED` and `REVIEWED` return `403`. Submitting requires `topicsCovered`,
`generalFeedback`, `tutorComment` and `progressRating`, plus `continuityNote`
whenever `continuityNeeded` is true. A month can only be submitted once per
student (`409 DUPLICATE_REPORT`), and no month beyond
`MAX_MONTHS_AHEAD` can be written at all (`400`).

Bulk import — CSV or XLSX, two steps:

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/api/admin/import/template/:type` | `tutors` · `students` · `assignments` |
| `GET` | `/api/admin/import/schema/:type` | Machine-readable column contract |
| `POST` | `/api/admin/import/:type?dryRun=true` | Preview only — writes nothing |

would skip as a duplicate, and every row it rejects with the reason and the
source line, so a bad spreadsheet is fixed before anything is written. A commit
is all-or-nothing.

## Notable implementation choices

**`bcryptjs`, not `bcrypt`.** Same API, pure JavaScript. The native `bcrypt`
needs a C++ toolchain on Windows, which is exactly the machine most people
develop this on. The cost is speed, which is irrelevant at login volumes.

**No `dotenv`.** `process.loadEnvFile()` is built in as of Node 20.6.

**Uploads are in memory.** Import files are capped at 5 MB, are held in memory
and are never written to disk — no temp-file cleanup, no path traversal, no
stale uploads. Only `.csv`, `.xlsx` and `.xls` are accepted, and exactly one
file per request.

**`multer` 2.x.** 1.x is unmaintained and carries advisories.

**`csv-parse` 7.x.** 5.x has a prototype-replacement advisory reachable through
the columns path.

**One place decides what a month is.** `resolveMonth()` in `src/lib/month.ts` is
the only thing that validates a `YYYY-MM` value and the only thing that enforces
"no future months". The autosave and submit paths therefore reject the same
input with the same `400`, rather than one returning 400 and the other 409.

### PDF export

`puppeteer` is an **optional** dependency, so a failed Chromium download never
breaks `npm install`. At runtime the exporter looks for a browser in this
order:

1. `PUPPETEER_EXECUTABLE_PATH`
2. Puppeteer's own bundled Chromium
3. Well-known Chrome/Edge/Chromium install paths on Windows, macOS and Linux

If none is found the endpoint returns a `400` explaining exactly which paths it
tried and which env var to set. Word (`.docx`) and HTML output have no such
requirement and are the safer default if a browser cannot be provisioned.

## Scripts

| Script | Does |
| --- | --- |
| `npm run dev` | `tsx watch`, reload on change |
| `npm run build` | `prisma generate` + `tsc` → `dist/` |
| `npm start` | `node dist/server.js` |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run setup` | generate + push + seed |
| `npm run seed` | Demo data; `-- --reset` clears first |
| `npm run db:push` | Sync schema without a migration |
| `npm run db:migrate` / `db:deploy` | Migration workflow |
| `npm run db:sql` | Regenerate `database/schema.sql` |
| `npm run db:studio` | Prisma Studio |

Re-running `npm run seed` on an already-seeded database creates **nothing** — it
confirms what is already there, including the tutor portal URLs. Two things make
that true:

- Rows are looked up by their natural key (`email`, `fullName`, `name`, and the
  `(tutor, student, course)` tuple) before being created, so existing data is
  reused rather than duplicated, and report rows go in with
  `skipDuplicates` against the `(assignment, month)` unique index.
- The **structure** of the data — which tutor gets which students, on which
  course, at which level — is derived from an FNV-style hash of the row ids
  rather than from the shared PRNG stream. This one is load-bearing, not tidiness.
  `prisma/seed.ts` picks the level only when it actually *creates* an assignment,
  so on a partly populated database the PRNG advances by a different amount than
  on a fresh one. Every later tutor then shuffles to a different set of students,
  so every later pairing differs — and because each new assignment brings a new
  `(assignment, month)` report with it, the totals grew on every single run
  (96 → 174 → 240 reports and climbing). Hashing the ids decouples the board from
  how far the PRNG happens to have advanced, which is what stops that cascade.

What the seed does **not** promise is byte-identical output across a `--reset`.
Prisma mints a fresh CUID per row and the tutor tokens are 48 hex characters of
`crypto.randomBytes`, so a reset legitimately produces different ids, different
pairings, and different portal links. That is the correct behaviour — reused
portal tokens across a data wipe would be a security problem, not a feature.
Within a single database, though, a re-run is fully stable.

Report *prose* (topics, attendance numbers, dates) still uses the PRNG. That is
fine: it is only ever written when a `(assignment, month)` row is first created,
and is never rewritten afterwards.

## Known issues

- **`next@15.1.6` in the sibling frontend carries CVE-2025-66478.** Not a
  backend problem, but it should be upgraded before the admin app goes live.
- **`xlsx` has no fix available on npm.** The SheetJS project moved
  distribution off npm; the fixes live in 0.19.3+ / 0.20.2+, which cannot be
  installed normally. It is reachable only through admin-only bulk import, where
  the file is size-capped, extension-checked, single-file and parsed in memory.
  Swapping it for `exceljs` (already a dependency, used for exports) would close
  the finding at the cost of a stricter reader.
- **`uuid`, pulled in transitively by `exceljs`,** is below 11.1.1. Only
  `uuid`'s buffer-taking `v3`/`v5`/`v6` are affected, which exceljs does not
  use. Fixing it means downgrading exceljs to a pre-3.5 release.
- **`PUPPETEER_EXECUTABLE_PATH` may need setting** on a server with no browser.
- Repeated smoke runs leave a few deactivated `Smoke Test…` rows behind. They
  cannot be deleted through the API by design; `npm run seed -- --reset` clears
  them.
